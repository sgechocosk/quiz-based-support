# Quiz-based Support

コードベースを調べて質問に答える代わりに、**穴埋めクイズ**で「システムとコードの理解」を促す VS Code 拡張です。
実装・修正の依頼では、AI が変更をまとめて書き換えるのではなく、**依存関係をたどって作った変更計画を、理由と確認の仕方とともに1ステップずつ**示します。

## 動作の流れ

1. サイドバー「コード思考」で質問・要望を入力(例: 「認証のフローを理解したい」「ログアウト機能を追加したい」)。書くのに迷ったら、入力中の候補と「依頼を整える」が手伝う([入力補助](#入力補助依頼を書く負担を減らす))。
2. エージェントがワークスペースを調査(ハイブリッド検索 BM25+ベクトル / grep / read_file / outline / LSP の定義・参照)。決まった回数を調べるのではなく、**何を知る必要があるかを先に決め、材料が足りたと確かめられたら終える**([調査](#調査))。
3. 質問の種類で分かれる。
   - **仕組みの質問**(「〜はどう動く?」)→ 読解のクイズ([読解のクイズ](#読解のクイズ))
   - **実装・修正の依頼**(「〜を追加したい」「〜にしたい」、またはモード「実装して学ぶ」)→ 実装の手順([実装の手順](#実装の手順))

### 調査

経験のあるエンジニアが初めてのコードベースで作業するときと同じ順序で調べます(`src/core/investigation.ts`)。

1. **手がかりを集める**: 要求の文そのもので索引を検索し、候補の場所(ファイル:行・シンボル名)を最初に示す。読んだことにはしない。
2. **調べることを決める**: 要求に答える(実装する)ために知る必要があることを、種類つきの問いにする(2〜6項目)。
   - 実装・修正の依頼: **変更する場所**(必須)・**手本**(同じ種類のことをしている既存の実装)・**定義**(新しいコードが使う関数・型)・**呼び出し元・入口**・**データ・画面・設定**(送る側と受ける側)
   - 仕組みの質問: **中心の処理**(必須)・呼び出し元・入口・定義
   - 決められなかったときは既定の項目(変更する場所+手本 / 中心の処理+呼び出し元)で調べる
3. **調べる**: 項目に沿ってツールで確かめる。互いに関係しない呼び出しは同時に行い、各結果に「残りの回数」と「まだ確かめていない項目」を添える。同じ呼び出しの繰り返しは回数に数えずに知らせ、上限を超える分は実行しない。
4. **材料が足りたかを確かめる**: 調査担当が終えたとき(または、まだの項目1つにつき2回程度調べたところ)で、項目ごとに「分かった(根拠の範囲)/不要(理由)/まだ」を答えさせる。
   - 「分かった」は、根拠の範囲を**実際に読んでいるときだけ**認める(検索結果の名前だけで判断したものは「まだ」に戻し、読むように伝える)
   - 変更する場所・中心の処理で使っているのに**定義をまだ読んでいない名前**を索引から見つけ、追加で調べるかを判断させる
   - 読んで初めて分かった項目(送る側に対応する受ける側など)は新しい項目として足す
   - まだの項目があれば、それと理由を伝えて調査を続ける。全部分かれば上限を待たずに終える
5. **まとめる**: 調査メモに「確かめた場所(種類・範囲・分かったこと)」「不要と判断したこと」「調べきれなかったこと」を書き、要件の整理・変更計画・出題に渡す。参照コードは、確かめた場所のファイル(変更する場所 → 手本 → 定義 …)を先に並べ、文字数に収まらなければその範囲の前後だけを残す(先に読んだ重要なファイルが後から読んだファイルに押し出されない)。

上限(`quizSupport.maxAgentSteps`、既定20回)は安全のためのもので、目安ではありません。材料の確認は1回の調査で3回まで、足りないと伝えても何も調べずに終えたらそこで打ち切ります。要件の回答を受けた追加調査(上限6回)と、段階に分けた依頼での段階ごとの調べ直し(上限8回)も同じ方式で進みます。段階ごとの調べ直しでは前の段階で読んだ行も根拠に使えるので、既に読んだ範囲で分かれば調べずに終わります。

この設計は、次のような調査・事例を参考にしています。

- 決まった回数や「ツールを呼ばなくなったら終える」だけでは、必要なファイルに一度も触れずに終える例が多い(Agent Retrieval Bench: 27〜35%)。一方で LLM は全体として十分かの判断が苦手(Kovrigin et al., 2024)なので、**項目ごとの判断に分け、根拠は機械的に確かめる**
- 知るべきことを先に分けてから順に絞り込む(Agentless の階層的な場所の特定、AutoCodeRover の「文脈は十分か」の確認、Claude Code の ToDo)
- 呼び出す関数・型の定義など依存先の文脈を集める(CodePlan、LocAgent のグラフ探索)
- 要求の文で検索した候補を最初の手がかりにすると、後の探索が減る(Agent Retrieval Bench の予備実験、Aider の repo map、Cursor の意味検索+grep)
- 残りの予算を見せると、むやみに使い切らずに済む(Budget-Aware Tool-Use, 2025)
- 文脈は多ければよいのではなく、編集するコードそのものが重要(ContextBench、"What Context Does a Coding Agent Actually Need to Act?")なので、重要な範囲を優先して渡す

### 実装の手順

1. **要件の整理**: 調査したコードをもとに、受け入れ条件(実装できたかを確かめられる振る舞い)と「変わる約束」(関数の引数・型・メッセージの種類など)を整理する。
   - **仕様や実装方針に複数の案がある**場合は、計画に進まずに先に要件を質問する(1〜3問・各2〜4個の選択肢。おすすめの案と補足の自由記述つき)
   - **変更が大きい**(約3か所・60行を超える見込み)場合は、依頼全体を完成させるまでの**段階**(それぞれ単独で動作が完結する、1回の手順で扱える大きさ)に分け、段階の分け方を見せてから進める。「今回どこまで実装するか」は聞かず、最後の段階まで進めて依頼全体を完成させる([大きな依頼](#大きな依頼段階に分けて完成まで進める))
   - 回答すると、選んだ案に関係するコードを追加で調査してから受け入れ条件を確定する。「確認せずに進める」で依頼のまま進めることもできる
2. **起点の変更**: 要件を直接満たす変更だけを LLM に書かせ、実ファイルには書き込まずに**仮想ワークスペース**へ重ねる。変更履歴で一緒に変わってきたファイルも手がかりとして渡す。
   - 編集は行番号ではなく「置き換える前のコード(oldCode)」を内容で探して当てる。完全一致から順に、行末の空白・インデント・空白全般・記号(全角や typographic な引用符)の違いを許して探し、インデントだけずれていれば置き換え後のコードも合わせる。複数か所に一致して決められないときは、別の場所を書き換えずに失敗とする
   - 構文はステップの編集をすべて入れた後で確かめ、壊れていればステップごと入れない(途中の状態は問わないので、開き括弧と閉じ括弧を別の編集に分けてもよい)。作り直しで同じ編集が返ってきたら、反映済みとして飛ばす
   - 出力が途中で切れた・読めない・ステップが空・編集のコードを写し間違えた、のいずれでも、理由と対象ファイルの今のコードを添えて最大2回作り直させる。写し間違いには、最も近い箇所と最初に食い違う行、構文エラーにはその行を添える
   - それでも作れなければ理由を表示し、実装の手順の代わりに実装のクイズで出題する(調査はやり直さない)
3. **影響の洗い出し(確認事項がなくなるまで)**: 変更の種類ごとの「変更伝播パターン」で、確認が必要な場所を機械的に集め、1か所ずつ「変更が必要か」を判断させて直す。直した変更からも、さらに確認事項を作る。
   | パターン | きっかけ | 探し方 |
   |---|---|---|
   | 呼び出し元の追従 | 関数のシグネチャを変えた・削除した | 言語サーバの参照検索(使えなければ単語検索) |
   | 振る舞いの変化の確認 | 戻り値・例外の扱いを変えた | 呼び出し元の参照検索 |
   | データ形状の追従 | 型・インターフェースのメンバーを変えた | 型の参照検索 |
   | 分岐の網羅 | 列挙値・ユニオン型の値を足した | 型の参照検索 |
   | キーの対応(送る側と受ける側) | メッセージの種類・設定キーなどの文字列キーを足した・消した | 同じキー、または同じ種類の既存のキーを文字列で検索(参照検索では見つからない結合) |
   | テストの追従 | テストから使われているシンボルを変えた | 参照のうちテストファイルのもの |
   | 一緒に変わってきたファイル | 過去のコミットで一緒に変更されることが多い | git の変更履歴 |
   | 型エラーの解消 | 変更を重ねた状態で新しい型エラーが出た | TypeScript の型検査(変更前からあるエラーは除く) |
   | プロジェクトの約束 | `.quiz-support/patterns.json` の条件に当てはまる | 約束に書かれた確認先 |
   - 判断は「変更した/変更不要(理由)/自動で直せず要対応」として記録する。判断できなかった確認事項・規模の上限(12ステップ・400行)は、最後に「手で確認が必要なこと」として示す
4. **手順に並べる**: 依存される側から(データ・型 → 中核の処理 → 呼び出し元 → 画面 → テスト → 設定 → 説明文)、引きずられた変更は元の変更の後に並べる。
5. **1ステップずつたどる**: 最初に手順の地図(サブゴールの一覧)を示し、各ステップで
   - **なぜ**: どの受け入れ条件のためか/どのステップの変更に引きずられたか(パターン名)
   - **約束の変化**と、変更の考えどころの**穴埋め**(選択式)
   - **予想: 次に確認すべき場所**(この変更のあと確認が必要になる関数を選ぶ。探し方のヒントつき)
   - 答え合わせの後に、**見つけ方(探し方・判断基準)と判断の結果**(変更した場所・変更不要と判断した場所とその理由)を表示。変更不要の場所は折りたたむ
   - 考えどころの少ない変更(import の追加など)は穴埋めにせず差分だけ見せる
6. **まとめと一括反映**: 正答数・手順の要約・反映するファイル(+/−行数)・型検査の結果・手で確認が必要なことを表示。すべてのファイルを1つの編集として反映する(計画のあとにファイルが変わっていたら反映しない)。反映後は「反映を取り消す」で戻せる。
7. **テスト(任意)**: `quizSupport.testCommand` を設定すると、反映後に保存してテストを実行できる(実行前にコマンドを表示して確認)。失敗したら、その内容で修正を依頼する文を入力欄に下書きする。

### 大きな依頼(段階に分けて完成まで進める)

1回の手順で扱える大きさ(約3か所・60行)を超える依頼は、段階に分けて**依頼全体が完成するまで**次のサイクルを回す。

1. **段階の分け方を決める**: 要件の整理で、依頼全体の受け入れ条件と、段階(名前・ねらい・段階ごとの受け入れ条件)を作る。各段階は依存される側から並べ、途中の段階でもビルド・既存の動作が壊れない大きさにする。案が複数ある点の質問と一緒に確認画面で見せる(回答に合わせて段階も見直す)
2. **段階ごとの手順**: 今回の段階だけを実装する変更計画を作る(計画・影響の判断には「依頼全体の中の何段階目か・済んだ段階・後の段階でやること」を渡し、後の段階の作業を先回りさせない)。いつもと同じく1ステップずつたどり、まとめから反映する
3. **次の段階へ**: 「次の段階へ進む」で、反映していなければ「反映して進む/反映せずに進む(自分で書いた場合)」を選ぶ。反映した変更は保存してから進む(次の段階の型検査はディスクの内容を読むため)
4. **残りの見直し**: 依頼全体の受け入れ条件と済んだ段階(反映したか・変更の要約)を見比べて、残りの段階を見直す。先に済んだものは除き、足りないものは足す。満たしていれば完成
5. **今のコードで調べ直す**: 前の段階で変わったファイルは今の内容で読み直し(変えた行の周り)、変わっていない行は前の調査の内容を使う。調査の会話は新しく始めて、古い行番号を引きずらない
6. 計画できなかった段階・中止した段階は、「計画し直す」か「飛ばして次へ」を選べる(飛ばした内容は残りの見直しで扱う)。1つの依頼で進める段階は最大8(超えたら残りを示して終える)
7. 最後に、進めた段階・依頼全体の受け入れ条件・変えたファイルをまとめて示す

### 読解のクイズ

1. **実際に読んだコードだけ**を根拠に、問題を生成。
   - LLM は「どの行のどの文字列を空欄にするか」だけを指定し、問題のコードはシステムが実ファイルから組み立てる(書き写しの食い違いで問題が落ちない。空白ゆれ・行番号ずれも吸収)
   - 読解: 実コードの一部を空欄化(正解で埋めると必ず原文に戻る)
   - 実装(change): LLM が書いた「置き換える前のコード(oldCode)」を内容で探して範囲を決め、変更後のコードの変更した行を空欄化。照合は変更計画の編集と同じ(空白・インデント・記号の違いを吸収し、複数か所に一致して決められなければ不合格、見つからなければ最も近い箇所を添えて作り直させる)
   - 構造クイズ: LSP から決定的に作る選択問題(呼び出し元・定義ファイル)
   - 不合格の問題は理由と実際の行内容を添えて作り直させる(合格した問題は残す)
   - 表示量の調整: 問題の範囲は空欄の前後3行まで自動で切り詰め、途中の無関係な行は「N行省略」に折りたたむ(クリックで展開)
2. 解答前に「読みどころ」と「参考にするコード」へのリンクを表示。
3. 空欄は**選択式**(正解1つ + 誤答3つ)。選んだ選択肢がコード中の空欄にはまって表示されるので、前後とのつながりを見ながら選べる → 段階ヒント(概念 → 考え方 → 手がかりの場所 → 誤りの選択肢を1つ消す) → 採点。
   - 誤答は「コードベースを読めば誤りと判断できる」もの(実在する似た名前の別の関数・変数、境界条件の違い、条件の反転、引数の取り違えなど)。コードベースに無い名前を含む誤答・正解と同じ書き方の誤答・長さで見分けがつく誤答は除外し、足りなければ正解の一部を実在する名前や反対の演算子に変えた誤答で補う
   - 採点後は、正解の理由と、自分が選んだ誤答が「なぜ違うか」だけを表示(他の誤答の解説は情報量を抑えるため出さない)
   - 先に予想するメモは任意(開いたときだけ入力欄を表示)
   - 解答前に見える文章(目標・課題文・ヒント・概念タグ・手がかり)は答えを含まないか機械判定し、漏れていれば LLM に書き直させ、それでも直らなければ伏せ字に置き換える(実装の手順の「なぜ」「約束の変化」も同様に確認)
   - 正解・解説は採点まで画面に渡りません(実装の手順では、答え合わせのたびに次のステップを渡す)
4. 判断の記録(観点別の一致率・Leitner 方式の振り返りカード)は workspaceState に保存。実装の手順の「次に確認すべき場所」の正誤は、パターン名ごとの正答率として残る。

## 入力補助(依頼を書く負担を減らす)

何をしたいかは決まっていても、「どの関数の名前だったか」「何を書けば伝わるか」を考えるのは負担になります。入力補助は、何をしたいかは利用者が決めたまま、その負担を減らして、調査と計画にうまく伝わる依頼にするのを助けます(`src/core/promptAssist.ts`・`media/assist.js`)。

| 機能 | いつ | API | 操作 |
|---|---|---|---|
| 続きの候補 | 入力が止まったとき(約0.8秒) | 使う(1回・短い出力) | 薄い文字で表示。Tab で全部、Ctrl/Alt/⌘+→ で1語ずつ入れる。Esc で消す |
| 名前の補完 | 英数字を3文字以上打ったとき | 使わない(索引) | 1つに決まれば薄い文字で、複数なら共通の先頭まで出して候補を並べる(選んで入れる) |
| 足すと伝わりやすくなること | 続きの候補が出ないとき | 使わない | 変更の依頼では「どうなってほしいか」、読み解きでは「知りたいこと」が書かれていなければ、それと「依頼を整える」を示す(場所は調査が探すので求めない) |
| 依頼を整える | ボタン・Ctrl+Enter | 使う(1回。規則に合わなければ作り直しでもう1回) | 書き直し案を、足した部分の印・「補ったこと」・補った名前の定義へのリンクつきで示す。あなたが決めることは選択肢で聞き(おすすめは付けない)、「入力欄に入れる」まで送らない |

Claude Code の「次のプロンプトの予測」にならい、次の方針で作っています。

- **勧めたい依頼ではなく、書こうとしている続きを予測する**: 書きかけは変えずに続きだけを足す。外れそうなら出さない
- **意図を変えない**: 読み解きの質問を変更の依頼に変える・別の依頼を足す・書きかけに無い条件(「〜とき」)や数値や画面の文言を足す候補は、規則で捨てる。依頼を整えるときも、決めていないことは〔 〕で空けて選択肢で聞き、置き場所や実装の方針は調べたあとの要件の確認に任せる
- **名前は実在するものだけ**: 候補に入れてよい名前は、書きかけ・構成の地図・書きかけで検索した手がかりに出てくる、索引に大文字小文字まで一致する名前だけ(索引のどこかにある、では見当違いの名前で調査が引っ張られるため)
- **後段に伝わる形にする**: 変更の依頼は「〜ようにしたい」、読み解きの質問は「〜はどう動く?」で終える(送ったあとの意図の判定に合わせる)。答えなかった決めることは、変更の依頼では「(まだ決めていない)」として送って調べたあとの要件の確認で決め、読み解きの質問では文から外す(読み解きには送ったあとの確認が無いため)
- **邪魔をしない・戻せる**: Enter は打った文だけを送る(候補は送らない)。入れた部分は次に打つまで下線で示し、Ctrl+Z で戻せる。IME の変換中・処理中は出さない
- **安く作る**: 指示・構成の地図・最近の依頼を先頭にそろえてプロンプトキャッシュに当て(公式エンドポイントでは `prompt_cache_key` を付ける)、推論なし・出力の上限つきで送る。同じ書きかけの結果は使い回し、同時に1件・1分に10回まで。新しく打ったら前の要求を中止する

自動の続きの候補は、次のときは呼びません。

- 書きかけが短い(5文字未満)・長い(400文字超・4行以上)・API キーなど秘密の情報らしい文字列を含む、索引がまだ無い
- API の設定(モデル名・ベースURL・キー)で作れなかった(設定を変えるまで)、混み合い・通信の失敗(1分→2分→5分休む)、応答が遅い(推論を止められないモデル)
- 候補を出せない・使われない状態が続いたときは、止めずに間隔を延ばす(候補が表示されたのに使わずに送った依頼が10件続いたら約1.6秒、20件で約3秒)。30件続いたら「設定」に、オフにできることを知らせる(止めるかはあなたが決める)

続きの候補を作るときは、送信前の書きかけ・最近の依頼(5件)・コードの構成(ファイルと主な名前)・書きかけで検索した場所(ファイル名と行番号・名前)を OpenAI API に送ります。設定 `quizSupport.inputAssist`(サイドバーの「設定」→「入力中の候補」)でオフにできます。テストモードの間は、入力中の候補(続きの候補・名前の補完)を出しません。「依頼を整える」は、オフでもテストモードでも使えます(テストモードでは実行前に確認します)。

## サイドバーの画面

仕組みはクイズ形式(候補から選んで確かめる)ですが、画面には試験のような言葉(問題・正解・出題・採点・〜問など)や点数、「学習」のような勉強のための言葉を出しません(学習用途に限らず、日々の開発でコードの理解を深めるための道具のため)。**プロのエンジニアが要件からどう考えて変更するか**を、番号つきの縦の流れで1段ずつたどる見せ方にしています。生成する文章にも同じ言葉づかいを指示しています(`src/core/level.ts` の `WORDING_RULE`)。

- 上部: 経験レベル・「判断の記録」(判断の一致率・見直したい観点・振り返り)・「設定」(APIキー・コード検索の索引・テストモード)。APIキーが未設定のときは上部に設定の案内を出す
- 仕組みの読み解き: ①何を理解するか → ②どこを、どう読むか(コードの中の要所を候補から選ぶ・考え方のヒント)→ ③呼び出し関係を確かめる → 「考えを確かめる」→ 振り返り(全体の流れ・見直すとよい判断)
- 変更の組み立て: ①要件の整理 → ②目標の設定 → ③実装するステップ → ④1ステップずつ実装する。各ステップは「変更の理由 → 変わる仕様 → 変更するコード(コードのすぐ上に変更する場所へのリンク)→ 影響はどこに及ぶか → 判断と根拠(影響の追い方)」の順。最後に変更の全体像と一括反映
- 実装前の確認: 案が複数ある依頼では決めることを選んでから「この方針で進める」。大きな依頼では段階の分け方も示す
- 段階に分けた依頼: 各段階のカードに「依頼全体をどう分けたか」(済んだ・今の・残りの段階)を示し、まとめから「次の段階へ進む」。最後に「依頼した変更が完成しました」として全体をまとめる
- 合っていたところは「✓ 合っています」とだけ示す。異なった・選ばなかったところは誤りとして赤で示したり判定を出したりせず、注意色で「`!ok` になる理由」として根拠へ読み進めてもらう(間違えたことより、直せることを重く見るため)
- スクロール: 送信したときはいちばん下へ、返答が届いたときは**その先頭**へ移動する(長い返答の最後に飛ばない)。考えを確かめたときは、選んだ場所で結果を確かめられるよう動かさない(使ったヒントは折りたたむ)。上の方を読んでいる間に届いたお知らせでは動かさず、「↓ 最新へ」を表示する

## テストモード

サイドバーの「設定」→「テストモード」(設定 `quizSupport.testMode`)をオンにすると、開発・検証向けの情報を表示します。オフ(既定)では、これらは表示も確認も行いません。

- API を呼ぶたびに**目的と入力トークン数(見積もり)**をダイアログで表示し、実行するか確認する
- 処理ごとの API 使用量、索引の件数(ファイル・チャンク・意味検索の進み具合)と埋め込みのトークン数、調査で決めた「調べること」の一覧、調査で呼んだツールと引数、作り直した問題の数、変更計画を作るときの注意、型検査を行わなかった理由

- 「この処理では以降確認しない」で、その依頼の残りの呼び出しをまとめて許可できる。取り消すと、その処理はそこで止まる
- 見積もりは文字数からの概算で、API が返す実際のトークン数で少しずつ補正する。処理の終わりに使用量(回数・入力・出力トークン)を表示
- オンの間は、ファイル変更時の埋め込みの自動更新を行わない(「設定」→「索引」の画面でトークン数を確認して更新する)
- オンの間は、入力中の候補(続きの候補・名前の補完)を出さない。「設定」に入力補助の記録(候補の表示・使用、依頼を整えた回数、補助を使った依頼と使わなかった依頼の調査の回数・要件の確認・見つからなかった数、候補を出さなかった理由、入力補助の API 使用量)を表示する

## プロジェクトの約束(`.quiz-support/patterns.json`)

「これを変えたら、あれも確認する」というプロジェクト固有の約束を書いておくと、変更計画の確認事項に加わります(熟練者の暗黙の判断を書き残す場所)。

```json
[
  {
    "name": "設定の登録",
    "when": { "literal": "^quizSupport\\." },
    "check": ["package.json", "README.md"],
    "criterion": "設定キーを足したら package.json の contributes.configuration と README の設定表にも書く"
  }
]
```

- `when.path`(変更したファイルの glob)か `when.literal`(足した・消した文字列キーの正規表現)のどちらかが必要
- `check` は確認するファイルのパスまたは glob。`howToFind` で探し方の説明も書ける

## セットアップ

- コマンド「コード思考: OpenAI APIキーを設定」またはサイドバーの「設定」→「OpenAI APIキー」で設定(SecretStorage に保存)。
- キー無しでもキーワード索引(BM25)は自動作成されます。意味検索(埋め込み)は「設定」→「索引」から有効化。

## 開発

```
npm install
npm run test:unit      # ユニット/E2E(偽OpenAI・実 TypeScript での型検査を含む)
npm run check-types && npm run lint
npm run compile        # esbuild(依存を全て同梱。型検査の TypeScript は同梱せず実行時に読み込む)
F5                     # Extension Development Host
npm run package:vsix   # .vsix 作成
```

## 既知の制限

- AST チャンク分割は ts/tsx/js/java のみ。他言語は行ベース分割。
- 宣言(シグネチャ・型のメンバー)の変化の判定は TS/JS/Java を想定した行単位の解析。型検査は TypeScript/JavaScript のプロジェクトだけ。
- 参照検索の精度は各言語の言語サーバに依存する(使えないときは単語の検索で代わりにする)。
- テストは仮想ワークスペースでは実行できないため、反映後に実行する。
- JSON ファイルは文字列キーの検索の対象にするが、索引(埋め込み)には入れない。
- 旧版の `vector-index` は使用しません(新形式は `index-v2`)。再索引は自動。
- 実 VS Code・実 OpenAI API での通し検証は開発環境では未実施です。
